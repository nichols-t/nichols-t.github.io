iamnotafake Protector Cryptosystem "Analysis"

Please note I am not a professional cryptographer, although I work with systems like this for a living. This could all be based around a standard I just haven't needed to work with yet. I just saw this online and was curious about it, and these are my notes on how I think this works.

Summary

The point of the iamnotafake device's cryptosystem is to allow verification that video footage containing a displayed pattern was genuinely recorded at the time that the video claims*.

*See the Open Questions section below--I'd like to know if this is correct, or if the verification is actually less specific than that.

Known Facts

  • Based on this Reddit post, we know that the displayed light is a "pattern computed with HMAC-SHA256 from the current time and a key unique to each pin".
  • The Youtube overview video states that "each device has a unique private key". In my work, the "private key" wording would mean to me that it's an asymmetric keypair, so I'll proceed with that assumption.
  • Verification is performed via the vendor website. I have not found details on how the verification works.

So we have at least 2 keys in play:

  • A device-unique symmetric key that performs an HMAC on the current time, and possibly on some other metadata.
    • I will call this the "Device-unique secret key" or DUSK.
  • A device-unique asymmetric keypair.
    • will call this the "Device-unique keypair" or DUKP. The public key will be called DUKPUB and the private key DUKPRI.

Assumptions

I will make the following assumptions:

  • All statements about the cryptography involved are accurate, but not necessarily complete.
  • The system is designed such that the vendor does not need to store the DUKPRI or the DUSK.
    • It could be the case that the vendor does store the DUSK or DUKPRI for each pin, but that would be undesirable if it can be avoided.

How I Think it Works

In order for the statements "The pattern is an HMAC... from a device-unique key" and "The device has a unique keypair" to both be true, and for the system to not require vendor-side storage of the DUKPRI, we would need to infer that either:

  1. The DUSK is generated randomly or derived from the DUKPRI.
  2. There are additional cryptographic elements involved.

If the DUSK is Generated/Derived With only the DUKPRI

The DUSK could be generated randomly. However, since the vendor needs to perform verification, it would need to either store or obtain the DUSK in some manner.

The site's verification page seems to just take the pattern (an HMAC result), and presumably a date from the video metadata as parameters. So we can be fairly sure that the DUSK is not being exchanged here.

If it is not being securely exchanged at verification time, then it would have to be stored by the vendor. However, the vendor would want to avoid needing to do this, so I think that the DUSK is *not* randomly generated.

Likewise, if one were to simply derive the DUSK via some KDF using the DUKPRI, then the vendor would have the same problem as the randomly-generated case: they'd need to store the DUKPRI to then re-derive the DUSK. Therfore I think there is at least one additional key involved.

A New Key

There is a way to create a shared secret without requiring one side (the device) to share the DUKPRI with another party: Diffie-Hellman (DH). DH allows the exchange of a shared secret between two keypairs, so I will invent a new keypair for this process.

I will call this the Vendor Key Pair or VKP, and corresponding VKPRI and VKPUB for its private and public components. The VKPRI can be stored vendor-side.

With the VKP, we can now derive DUSK as the shared secret* from a DH between the VKP and the DUKP. This would allow the DUKPRI to remain only on the device. At provisioning time, the VKPUB would be sent to each device, and the device would send its DUKPUB to the vendor.

Now, each side can derive the shared secret at any time, and the DUKPRI can remain solely on its own device without needing to be persistently stored by the vendor.

*I believe it's recommended to not use the shared secret directly as the DUSK but to perform a KDF on the shared secret first to produce the DUSK. If I were less lazy I would find the NIST standard to this effect.

Verification

If the DH above is being done, the vendor can verify a code by:

  1. Knowing which pin produced the HMAC pattern.
    • Preumably this metadata would be stored by the vendor, or is an undocumented part of the pattern
    • Some comments say that the verify searches for any matching pin, which would make this requirement moot (but this feels like something that the vendor maybe ought not to be doing)
  2. Performing a DH using the stored DUKPUB for that device and VKPRI.
  3. Performing the HMAC on the claimed timestamp and any other necessary metadata.
  4. Comparing the results to see if they match.

Open Questions

What is the actual cryptographic scope of the verification?

  • Does it verify that this pin produced this pattern at this time?
  • Does it verify that this pin produced this pattern at some point in the past?
  • Does it verify that any pin produced this pattern at some point in the past?

Why is verification seemingly a vendor-controlled process, instead of being something that anyone can perform?

What device-unique information (whether keys or other metadata) does the vendor actually store?

Is there any mechanism to verify the authenticity of a device?

I.e. is the device-unique keypair tied to a certificate? If so, what root signs this certificate and how is that root secured?

Conclusion

This is an interesting product idea; I am probably not going to buy it at that price, and certainly not without knowing how the cryptography works. I think the vendor ought to publish a page explaining the cryptosystem,as a secure cryptosystem is not weakened if its details are made public.

There are other ways that the system could be circumvented; the reddit post above has a few mentions of these, which the vendor acknowledges. Nevertheless, I like the spirit of the product. Even if the defense that this product provides is imperfect, I am glad that some work is being done to defend against misinformation and altered content.
